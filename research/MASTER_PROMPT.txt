PROFESSOR SWARM REAL OPEN-SOURCE BUG INVESTIGATION
6804 indexed question blocks; 17 populated core themes; 20 individually sourced real-world defect investigations.
The original 6804 blocks are conceptual questions, NOT 6804 independently verified defects. A theme label can differ from the row's focal question; never turn an index tag into fabricated proof. Each dossier contains one upstream issue, patch, documented defective behavior, or acknowledged limitation and tells which evidence grade applies.

OUTPUT RULES
For each real defect, use the customer's first actual action, the first concrete code path, and the operator's failure observation. Write the state before each action and the state after it, moving from observed bytes, object lifetimes, queue positions, packet decisions, and commit evidence to the necessary invariant. Identify the missing mental connection rather than guessing a developer's intelligence or intention. Separate a documented root cause from a plausible interpretation. Count only real numbers found in a source, a reproducible measurement, or a mathematically derived boundary. No fabricated examples or toy scenarios. Challenge the model with a hard failure-chain puzzle derived from the defect and reveal exactly why the bad chain fails; omit a ready-made source patch. Show successful path and failing path with true/false predicates. Verify one operation on one process and one machine before asserting multiple operations, then four users and a second machine; do not inflate scale before proof of single-operation correctness. Preserve all necessary original relationships rather than replacing them with unrelated stories. Link upstream evidence and document what still needs a local run.

ADDED QUESTIONS FOR EVERY BUG
What actually failed for a user?
What action entered the first faulty code path?
Where did the original value, object identity, reference, generation, or commitment evidence enter?
What exact state changed between the last safe decision and the first unsafe decision?
Why was the previous state insufficient to justify the next one?
Where did an equality comparison erase an identity required downstream?
What work did an apparently harmless cache, optimization, or monitoring operation introduce?
What independent event made a previous proof stale?
What hidden dependency did the developer fail to model?
How does the working path preserve correctness for one operation?
How does the failing path violate correctness before scale is introduced?
What observation distinguishes the source code's intent from actual behavior?
Which exact source line, upstream patch, issue, crash report, or test establishes the defect?
Which link is necessary for correctness, and what downstream state collapses if removed?
Where does memory lifetime end while a pointer remains visible?
Where does a count cease to represent original input because a previous conversion lost information?
Where does a byte sequence gain a different meaning because of CPU endianness or format version?
Where does a name or lookup key stop identifying the same object?
Where can a queue retry indefinitely without decreasing remaining work?
When does one observer's diagnostic re-enter the observer and make event count grow?
Where do replicated writes become durable, and what evidence does a client actually receive?
Which exact tests establish success, failure, error reporting, crash recovery, and bounded completion?
How does one customer operation remain correct before two, a thousand, four users, and another machine are admitted?
Where is the hard conceptual mistake, not a low-value syntax, offset, or counting mistake?
What is verified, what remains unverified, and what local experiment can resolve the gap?

PUZZLE RULE
Use only the real source defect for the harder puzzle. Expose the complete broken dependency chain and necessary invariant. Do not invent scenarios, values, statistics, or code. Do not provide a source-level patch as an answer. Show exact transition and why its alternative breaks. No attribution of low intelligence to engineers.

EVIDENCE CONSTRAINT
A verified issue report is proof of reported symptoms, not automatically proof of the reporter's root-cause theory. A published patch explanation is stronger for cause. A source comment documents a design safeguard but does not by itself establish a separate historical bug report. A published regression test is stronger still. All cases state what has NOT been tested locally.
